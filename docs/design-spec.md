# SEO Routine Skill — Design Spec

**Date:** 2026-03-11
**Status:** Approved
**Goal:** Build a reusable, project-agnostic `/seo-routine` skill that grows organic traffic through data-driven weekly content and technical SEO optimization cycles with prediction tracking.

---

## 1. Architecture

Two-layer design:

**Core engine** (reusable, project-agnostic) — the `/seo-routine` skill. Knows how to collect SEO data, score opportunities, plan weekly work, implement changes, and track predictions vs actuals over time.

**Project adapter** (generated during calibration) — a `seo-config.md` file in the project that tells the core engine how the project's content pipeline, SEO infrastructure, data sources, competitors, and goals are structured.

### Calibration Flow

First run: `/seo-routine calibrate`

**Phase 1 — Auto-discovery (no questions):**
- Scan for content files: `**/*.md`, `**/*.mdx`, `**/articles/*.js`, `**/content/**`, `**/posts/**`
- Detect CMS: Strapi, WordPress, Contentful, headless patterns
- Find SEO infrastructure: `sitemap.ts`, `robots.txt`, `schema.*`, `llms.txt`
- Detect framework: Next.js, Nuxt, Astro (determines how content reaches production)
- Check for analytics config: GA4, Umami, Plausible
- Read `CLAUDE.md` / `package.json` for project context

**Phase 2 — Targeted questions (3-5 max):**
- Site production URL
- SEO data root directory (default: `docs/seo/`, suggest alternatives like `seo/`, `marketing/seo/`). All generated files, weekly reports, and inputs live under this root. The config, goals, scorecard, forward-log, and `weeks/` subdirectory are all relative to this path.
- Top 3 competitors
- Available data sources (checkboxes, pre-filled from auto-detection)
- For each enabled data source: verify credentials exist (env vars, config files) or guide setup
- Current strategic goal (optional)

**Phase 3 — Generate `docs/seo/seo-config.md`:**

The config uses a fenced YAML block inside a Markdown file. The skill parses only the content within the `yaml` fence. Values shown below are examples for a real project — no alternatives or placeholders.

```markdown

\```yaml

**Credential verification during calibrate:**
For each enabled data source, the calibration phase checks if the required environment variables exist. If missing, it prints setup instructions specific to that source (e.g., "Create a GCP service account with Search Console read access, download the JSON key, and set GOOGLE_APPLICATION_CREDENTIALS=/path/to/key.json"). Data sources with missing credentials are marked `enabled: false` with a comment explaining what's needed.

**Phase 4 — Scaffold directory structure:**

Calibration creates all required files and directories under the configured root (e.g., `docs/seo/`, `seo/`, `marketing/seo/`):

```
{root}/
  seo-config.md                    # generated from phases 1-3
  goals.md                         # empty template with Active Goal / Previous Goals sections
  scorecard.md                     # empty table with column headers (Week, Pages Optimized, Avg Position, Clicks, Impressions, CTR, Prediction Accuracy)
  forward-log.md                   # empty table with column headers
  weeks/                           # empty, populated by analyze phase
    .gitkeep
```

Claude memory (created via Write tool):
```
memory/seo/
  state.md                         # initialized with calibration date, root path, no runs yet
  learnings.md                     # empty with section headers
  keyword-tracker.md               # empty with column headers
```

If `{root}/` already exists (re-calibration), only `seo-config.md` is overwritten. Other files are preserved.

Re-calibration: run `calibrate` again to update. Reads existing config, shows diffs.

## 2. Data Collection & Scoring Model

### Data Sources

**Automated collectors (run via multiple independent `Agent` tool calls in a single message for concurrency):**

| Source | What it provides | API/Method |
|--------|-----------------|------------|
| GSC | Clicks, impressions, CTR, avg position per page/query (7d vs prev 7d) | Search Console API via service account |
| Umami/GA4 | Page views, bounce rate, session duration per page | Analytics API |
| DataForSEO | SERP positions for tracked keywords, competitor positions | DataForSEO REST API (rate limit: 2 req/sec, retry with exponential backoff) |
| Self-crawl | Schema validation, meta tags, content length, internal links, heading structure, image alt text | Fetch + parse (no browser needed). Core Web Vitals via PageSpeed Insights API (1 req/sec, 3s backoff on 429) |

**Self-crawl scope:** Controlled by `self_crawl` config. Default: crawl up to 50 pages from sitemap. Can also be set to `scored` (only pages that appear in the scoring pipeline) or `manual-list` (explicit URL list in config). Core Web Vitals measured via PageSpeed Insights API (fast, no local Lighthouse needed) unless config overrides to `lighthouse`.

**Manual inputs (dropped before running analyze):**

| Source | Format | Location |
|--------|--------|----------|
| Ahrefs | CSV/PDF exports | `docs/seo/weeks/YYYY-WNN/inputs/` |
| Manual notes | Markdown | `docs/seo/weeks/YYYY-WNN/inputs/notes.md` |

### Composite Scoring Model

Each page or keyword opportunity gets a score (0-100):

| Signal | Default Weight | Formula |
|--------|---------------|---------|
| Striking distance | 25% | `score = 100` if position in [5,10] and impressions >= 100/wk; linearly scales to `0` at position 20 or impressions < 10/wk. Position < 5 scores 50 (already ranking well). Position > 20 scores 0. |
| CTR gap | 20% | Uses expected-CTR-by-position curve (AWR benchmarks: pos 1=31%, pos 2=16%, pos 3=11%, pos 5=7%, pos 10=2.5%). `score = max(0, (expected_ctr - actual_ctr) / expected_ctr * 100)`. High score = page underperforming its position. |
| Content quality | 15% | Checklist-based: word count < 800 (+30), no FAQ section (+20), no schema markup (+15), no internal links (+15), missing meta description (+10), no images (+10). Sum capped at 100. |
| Technical debt | 15% | Checklist-based: missing canonical (+25), missing schema (+20), broken meta tags (+20), no og:image (+15), missing alt text on images (+10), CWV issues (+10). Sum capped at 100. |
| Keyword gap | 15% | For each keyword where a competitor ranks in top 20 and we don't: `score = (competitor_impressions / max_impressions) * 100`. Top gap keyword score used. |
| Goal alignment | 10% | Binary bonus: if the page/keyword matches a target in `goals.md` (keyword overlap or URL match), score = 100. Otherwise 0. |

**Final composite score** = weighted sum of all signal scores, normalized to 0-100.

Weights are configurable in `seo-config.md`.

### Weight Adjustment Feedback Loop

The `review` phase tracks prediction accuracy per signal type. Weight adjustments are applied as follows:

- **Threshold:** 4+ data points (predictions) for a signal type required before adjustment
- **Adjustment rule:** For each signal type, calculate hit rate (Hit or Partial / total predictions). If hit rate < 40% over the last 8 predictions, reduce weight by 3 points. If hit rate > 75%, increase weight by 2 points. Weights are clamped to [5, 40] and re-normalized to sum to 100.
- **Storage:** Effective weights (after adjustment) are written to `memory/seo/learnings.md` under a `## Effective Weights` section. The skill reads effective weights from `learnings.md` first, falling back to `seo-config.md` defaults if no adjustments exist yet.
- **Reset:** User can delete the `## Effective Weights` section from `learnings.md` to revert to config defaults.

## 3. Phases

### Phase 1: Analyze (`/seo-routine analyze`)

1. Read `seo-config.md` for project context
2. Create `docs/seo/weeks/YYYY-WNN/` directory if not exists
3. Collect data from all configured sources (parallel subagents)
4. Parse any manual inputs from `inputs/`
5. Score all pages and keyword opportunities
6. Identify top movers (improved/declined vs last week)
7. Write `docs/seo/weeks/YYYY-WNN/analysis.md`

Can run in background via `/loop 7d /seo-routine analyze`.

### Phase 2: Plan (`/seo-routine plan`)

1. Read analysis for current week
2. Read `forward-log.md` — skip pages touched in last 3 weeks
3. Select top opportunities within weekly budget (3-5 content + 2-3 technical)
4. Classify each as content-only or technical
5. For each item, specify: what to change, why, expected metric impact, prediction timeline
6. Append predictions to `docs/seo/forward-log.md`
7. Write `docs/seo/weeks/YYYY-WNN/plan.md`
8. Present plan for user approval before proceeding

### Phase 3: Implement (`/seo-routine implement`)

Reads approved plan, executes in a git worktree on branch `seo/YYYY-WNN`:

| Change Type | Scope | QA Level |
|------------|-------|----------|
| Content optimization | Edit article seed files, rewrite sections, improve meta/FAQ/E-E-A-T | Diff review (lightweight) |
| New content | Create new article file + add to index, add redirect if needed | Diff review |
| Schema/sitemap/technical | Edit schema generators, sitemap, llms.txt, redirects | Full QA — build + test |
| Route/component changes | Edit pages, components, nav, footer | Full QA — build + E2E |

All changes go into a single feature branch per week. Content and technical changes are separate commits.

Auto-generates `docs/seo/weeks/YYYY-WNN/changes.md` with commit SHAs and change descriptions.

### Phase 4: Review (`/seo-routine review`)

Run at start of next week (or anytime):

1. Read `forward-log.md` for predictions whose "by when" has arrived
2. Pull current data from GSC/DataForSEO for affected pages
3. Compare actual vs expected
4. Fill in "Actual" and "Status" columns (Hit / Partial / Miss)
5. Score prediction accuracy
6. Update `docs/seo/scorecard.md`
7. Write learnings to Claude memory (`memory/seo/learnings.md`)

## 4. Directory Structure

### Git-tracked (`{root}/` — default `docs/seo/`, configurable)

```
{root}/
  seo-config.md                    # project adapter (generated by calibrate)
  goals.md                         # active strategic goals
  scorecard.md                     # global metrics table, updated weekly
  forward-log.md                   # predictions: "did Y → expect X by week Z"
  weeks/
    2026-W11/
      inputs/
        ahrefs-organic-keywords.csv
        ahrefs-backlinks.csv
        notes.md
      analysis.md
      plan.md
      changes.md
    2026-W12/
      ...
```

All phases read `root` from `seo-config.md` to resolve paths. The `state.md` in Claude memory also caches the root for quick lookup.

### Claude memory (`.claude/projects/.../memory/seo/`)

```
memory/seo/
  state.md            # last run date, current week, active branch
  learnings.md        # what works/doesn't for this site (from review phase)
  keyword-tracker.md  # tracked keywords + last known positions
```

**Memory retention policy:**
- `state.md` — always current, overwritten each run (~10 lines)
- `learnings.md` — rolling window of last 12 weeks of learnings. On each review, if entries exceed 12 weeks, the oldest are summarized into a `## Historical Summary` section (1-2 lines per quarter). Max file size: 200 lines.
- `keyword-tracker.md` — tracks up to 100 keywords with last 4 weekly positions. Older position data is dropped. Keywords not seen in 8 weeks are pruned.

### Goals Format (`goals.md`)

```markdown
# Strategic Goals

## Active Goal
objective: "Rank top 5 for 'sync google calendars'"
target_keywords:
  - "sync google calendars"
  - "google calendar sync tool"
  - "two way calendar sync"
target_pages:
  - /blog/sync-two-google-calendars
  - /blog/how-calendar-sync-works
deadline: 2026-W20
success_metric: "avg position < 5 for primary keyword"

## Previous Goals
<!-- Completed/abandoned goals archived here with outcome -->
```

The `goal_alignment` scoring signal checks whether a page URL matches `target_pages` or a keyword matches `target_keywords`. If either matches, the signal scores 100.

### Forward Log Format (`forward-log.md`)

Uses structured columns for machine-parseable predictions. The `Metric`, `Baseline`, and `Target` columns enable the `review` phase to automatically pull the correct data and compare.

```markdown
# Forward Log

| Week | Action | Target Page/Keyword | Metric | Baseline | Target | By When | Actual | Status |
|------|--------|---------------------|--------|----------|--------|---------|--------|--------|
| W11 | Rewrote meta + FAQ | /blog/sync-two-google-calendars | position | 14 | 8 | W14 | | Pending |
| W11 | Rewrote meta + FAQ | /blog/sync-two-google-calendars | ctr | 1.2% | 3.2% | W14 | | Pending |
| W11 | New article | /blog/outlook-calendar-sync | position | — | <30 | W13 | | Pending |
| W11 | Fixed schema | /compare/* (5 pages) | rich_results | 0 | 3+ | W14 | | Pending |
```

**Supported metric types:** `position`, `ctr`, `clicks`, `impressions`, `rich_results`, `indexed` (boolean), `cwv_lcp`, `cwv_cls`.

**Baseline:** Current value at time of prediction. Use `—` for new content (no baseline).

**Target:** Expected value. Supports comparators: exact number, `<30`, `3+`, `+50%` (relative).

The `review` phase:
1. Reads rows where `By When` <= current week and `Status` = Pending
2. Pulls the `Metric` value for `Target Page/Keyword` from GSC/DataForSEO
3. Fills `Actual` column
4. Sets `Status` based on how much of the target delta was achieved:
   - **Hit:** achieved >= 75% of the target delta (e.g., baseline=14, target=8, delta=6 → actual <= 9.5)
   - **Partial:** achieved 25-74% of the target delta (e.g., actual 10-12 in the example above)
   - **Miss:** achieved < 25% of the delta, or regression (e.g., actual >= 12.5 or worse than baseline)

## 5. Command Interface

```
/seo-routine calibrate           # Discover project, ask questions, generate config
/seo-routine analyze             # Collect data, score pages, produce analysis
/seo-routine plan                # Pick top items, create plan, update forward-log
/seo-routine implement           # Execute plan in worktree (seo/YYYY-WNN branch)
/seo-routine review              # Compare predictions vs actuals, update scorecard
/seo-routine status              # Current week, pending work, last run summary
/seo-routine goals "..."         # Set/update strategic goal
```

### Typical Weekly Flow

```
Monday:
  1. Drop Ahrefs CSVs into docs/seo/weeks/YYYY-WNN/inputs/
  2. /seo-routine analyze         → background: produces analysis.md
  3. /seo-routine plan            → produces plan.md, user reviews + approves

Tuesday-Thursday:
  4. /seo-routine implement       → creates branch, makes changes, QA on technical
  5. Review PR, merge

Next Monday:
  6. /seo-routine review          → fills in actuals for past predictions
  7. Back to step 1
```

### Loop Integration (Hybrid Automation)

```
/loop 7d /seo-routine analyze    # Auto-analyze every Monday
```

User manually runs `plan` → `implement` when ready.

### Error Handling

- Missing data source → skip, note in analysis what's missing
- No `seo-config.md` → prompt to run `calibrate`
- No manual inputs dropped → run with automated sources only, flag gap
- Build/test failure during implement → stop, report error, don't commit broken code

### What Lives Where

| Component | Location | Why |
|-----------|----------|-----|
| Skill logic (SKILL.md) | Plugin repo | Reusable across projects |
| Scripts & references | Plugin repo | Reusable knowledge base |
| Templates | Plugin repo | Scaffolding source |

| Operational state, learnings, keyword tracker | Target project Claude memory | Session continuity |

### No External Dependencies

- Standard Claude Code tools only (Bash, Read, Write, Edit, Agent, WebSearch, WebFetch)
- **Data source integrations** use the bundled Python scripts when DataForSEO is enabled, or fall back to WebFetch/Bash for other APIs
- Scripts from the plugin are referenced by their plugin-relative paths (Claude Code resolves plugin paths automatically)

### Dry-Run Mode

`/seo-routine implement --dry-run` shows what would be changed (file paths, diff previews, QA classification) without writing any files. Useful for building trust in the tool and reviewing the plan's impact before committing.

### Rate Limiting

All external API calls use backoff/retry:
- **DataForSEO:** max 2 requests/sec, exponential backoff on 429 (1s, 2s, 4s, max 3 retries)
- **PageSpeed Insights:** max 1 request/sec, 3s backoff on 429
- **GSC API:** max 5 requests/sec (Google default), standard retry on 429
- **Self-crawl of own site:** 500ms delay between requests to avoid triggering CDN/WAF rate limits

### Relationship with Existing seo-geo Skill

The Python scripts from the existing `.claude/skills/seo-geo/` skill are **migrated into the plugin repo** under `scripts/`. This is the canonical location — projects that had the old `seo-geo` skill can remove it after installing the plugin. The `tools.seo_geo_scripts` config key is no longer needed; scripts are always available via the plugin path.

The skill does NOT:
- Require any specific framework or CMS
- Hardcode any project-specific paths or URLs
- Depend on other skills at runtime (fully self-contained plugin)
- Need a separate installation step beyond `calibrate`
